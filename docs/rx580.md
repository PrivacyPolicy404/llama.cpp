# Running a 125B MoE on an RX 580: setup, options and how to reproduce

This page belongs to the fork (branch `ot-host-buffers`), not to upstream llama.cpp. It has what the summary in the
README leaves out: the exact files and commands, what every option is there for, what each patch changes in the
code, and how the numbers were measured so you can check them on your own card.

Everything here was measured on one machine. Expect different absolute numbers on yours; the method section is
there so you can tell which parts carry over.

## The machine

| | |
|---|---|
| GPU | Radeon RX 580 8 GB (Polaris 10, GCN4), PCIe 3.0 |
| Driver | Mesa 25.2.8 RADV, kernel 6.8 (Ubuntu 24.04) |
| CPU / RAM | i7-10700 (8 cores), 64 GB DDR4-3200 (XMP on, ~43 GB/s) |
| Storage | NVMe for the model files |

What the card lacks, and why it matters: no fp16 arithmetic (`shaderFloat16`), no accelerated integer dot product,
no cooperative matrices. Several Vulkan paths in llama.cpp assume one of those and fall back to slower code or to
the CPU. Check yours in the first log line of any run:

```
ggml_vulkan: 0 = AMD Radeon RX 580 Series (RADV POLARIS10) (radv) | uma: 0 | fp16: 0 | bf16: 0 | warp size: 64 | int dot: 0 | matrix cores: none
```

## Build

```bash
git clone -b ot-host-buffers https://github.com/PrivacyPolicy404/llama.cpp
cd llama.cpp
cmake -B build -DGGML_VULKAN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --target llama-server llama-quantize test-backend-ops -j 8
```

`GGML_NATIVE` and OpenMP stay at their defaults (on). Patch 5 needs AVX2.

## The model files

Source: [SC117/Qwen3.8-Flash-Next-GSQ-RCO-abliterated-GGUF](https://huggingface.co/SC117/Qwen3.8-Flash-Next-GSQ-RCO-abliterated-GGUF).
Download the two `Q2_0/` shards (66 GB) and `mtp-Qwen3.8-Flash-Next-Q4_0.gguf` (the MTP draft block), and verify
the sha256 of each against the Hugging Face API. Put them on an NVMe: the second shard holds an n-gram table
(28.8 GB) that is read from disk one row per token.

Two files are then derived from those.

**1. Hyper-connections in Q8_0** (needs patch 3). The hyper-connection weights ship in BF16 (1.2 GiB) and sit on
the GPU:

```bash
build/bin/llama-quantize --keep-split --tensor-type 'hc_(attn|ffn)_(up|down)=q8_0' \
    Qwen3.8-Flash-Next-GSQ-RCO-abliterated-Q2_0-00001-of-00002.gguf \
    Qwen3.8-Flash-Next-GSQ-RCO-abliterated-Q2_0-hcq8.gguf COPY 8
```

Result: 0.55 GB less VRAM, +2-3 % speed. Quality against the original with `llama-perplexity --kl-divergence`
(12 x 512 tokens): perplexity 0.9988x, mean KLD 0.0077, same top token 97.5 % of the time.

**2. MTP draft with a reduced output vocabulary** (needs patch 8). The draft block spends more than half of its
time in the output projection (248320 rows). The trimmed file keeps only the rows of the K most frequent tokens:

- `output.weight` has K rows instead of the full vocabulary;
- a new tensor `d2t` (I64, K values) gives the token id of each row.

The engine scatters those K logits over the full vocabulary and leaves the rest at -inf. The target model still
verifies every draft against the full vocabulary, so the output distribution does not change; a draft token outside
the K simply cannot be proposed. K = 65536 here, ordered by frequency over ~13 M tokens of Spanish and English news,
Wikipedia, code and chat; it covers 99.7 % of the tokens in real outputs. The first 65536 token ids cover only
92.9 %, so the order has to come from a frequency count, not from the ids.

The two scripts that build it are in `scripts/mtp-d2t/` of this fork (plain Python, no dependencies):

```bash
# 1. rank the vocabulary by frequency, with the model loaded in a running llama-server
python3 scripts/mtp-d2t/mtp_vocab_order.py order.json --n-vocab 248320 --first-special 248000 \
    --server http://127.0.0.1:8080 --held-out some-real-outputs.txt \
    2:spanish-news/ 1.5:spanish-wikipedia/ 1:english-news/ 1:english-wikipedia/ 1.5:code/ 3:chats/

# 2. trim the draft
python3 scripts/mtp-d2t/gguf_mtp_d2t.py mtp-Qwen3.8-Flash-Next-Q4_0.gguf \
    mtp-Qwen3.8-Flash-Next-Q4_0-d2t65k.gguf order.json 65536
```

Each `WEIGHT:PATH` is a text file or a directory; use text that looks like what you generate. The sentence corpora
used here are the 100K sets from [Leipzig](https://wortschatz.uni-leipzig.de/en/download). `--held-out` prints
which share of a text that was not used for the ranking the first K tokens cover: pick the smallest K that stays
above ~99.5 %. Without a `d2t` tensor the patch does nothing, so the stock draft file works too, about 2 % slower
and with 0.24 GiB more VRAM.

## System settings

- **Pin the memory clock.** The GPU works in bursts and amdgpu halves the memory clock in the pauses:
  ```bash
  cd /sys/class/drm/card1/device      # the card that has pp_dpm_mclk
  echo manual | sudo tee power_dpm_force_performance_level
  echo 2      | sudo tee pp_dpm_mclk  # the highest state listed in the file
  ```
  +2-3 % with MTP. Set `power_dpm_force_performance_level` back to `auto` when done.
- **Pinned memory (GTT) is capped at half of the RAM** by amdgpu: 31 GiB here. The run below pins 29.4 GiB. With
  less than 64 GB of RAM, pin fewer expert layers (see `-ot` below).
- **Close the desktop for 64K of context.** KDE holds ~415 MiB of VRAM. With a desktop running, ~48K is the most
  that fits with margin. If you run headless, the user needs the `render` and `video` groups or Vulkan silently
  falls back to llvmpipe (2 tok/s).
- One user, one slot. Nothing else on the GPU.

## The command

```bash
export GGML_VK_VISIBLE_DEVICES=0
export GGML_VK_MAX_NODES_PER_SUBMIT=16
export GGML_VK_FIRST_SUBMIT_NODES=2

build/bin/llama-server \
  -m Qwen3.8-Flash-Next-GSQ-RCO-abliterated-Q2_0-hcq8-00001-of-00002.gguf \
  -ngl 99 -t 8 -np 1 -c 65536 -b 2048 -ub 2048 --reasoning off \
  -lm none --lazy-mode on --no-host \
  -ot 'blk\.([0-9]|[1-3][0-9]|4[0-3])\.ffn_.*_exps=Vulkan_Host,ffn_.*_exps=CPU' \
  -ctk q8_0 -ctv q8_0 -ctkd q8_0 -ctvd q8_0 \
  --spec-type draft-mtp --spec-draft-model mtp-Qwen3.8-Flash-Next-Q4_0-d2t65k.gguf \
  --spec-draft-n-max 2 --spec-draft-n-ubatch 512 \
  --spec-draft-sampling probabilistic --spec-draft-p-min 0
```

Wrap it in a memory limit while you experiment, so a wrong flag kills the server and not your session:
`systemd-run --user --scope -p MemoryMax=58G -p MemorySwapMax=0 build/bin/llama-server ...`

## What each option is for

| Option | Why | Measured effect here |
|---|---|---|
| `-lm none --lazy-mode on` | do not load or map the whole file; the n-gram table is read from NVMe per token | the model would not fit in RAM otherwise |
| `--no-host` + `-ot ...=Vulkan_Host,...=CPU` | pin the experts of layers 0-43 in host memory and leave 44-47 unpinned, to stay under the GTT cap (patch 1) | long prompt 104 -> 125 tok/s; pinning all 48 loses the Vulkan device |
| `-ngl 99` | the dense part (4.7 GiB) goes to the GPU; the experts stay in RAM because of `-ot` | |
| `-np 1` | the default 4 slots split the context and eat pinned memory | 4 slots run at half the speed |
| `-b 2048 -ub 2048` | larger prompt batches | long prompt 62 -> 104 tok/s; 4096 is much worse (45) |
| `-ctk/-ctv/-ctkd/-ctvd q8_0` | K/V cache in Q8_0 for model and draft | 64K takes 1.0 GiB instead of 1.9; KLD 0.0035; ~3 % slower |
| `-c 65536` | context | 80K does not fit, see below |
| `--spec-type draft-mtp`, `--spec-draft-n-max 2` | MTP speculative decoding, 2 draft tokens | +30 % generation; 3 and 4 drafts are slower with sampling |
| `--spec-draft-n-ubatch 512` | the draft context otherwise reserves buffers for the full `-ub` | 0.42 GiB less VRAM, same speed |
| `--spec-draft-sampling probabilistic --spec-draft-p-min 0` | the draft samples and the target verifies by rejection (exact) | acceptance 72 -> 75 % at temp 0.8, +2.3 % |
| `GGML_VK_MAX_NODES_PER_SUBMIT=16` | submit GPU work more often; splits are short (~53 nodes) | +1.4 % |
| `GGML_VK_FIRST_SUBMIT_NODES=2` | submit the first batch of each graph after 2 nodes (patch 7); off by default | +2.9 % without MTP, +0.8-1.4 % with |
| `--reasoning off` | preference, not performance | |

Sampling settings do not matter for speed except the temperature: at temperature 0 the draft acceptance is higher
and the runs are repeatable, which is why the comparisons below use it.

## What each patch changes

One commit per patch; `git log upstream/master..ot-host-buffers` lists them with their measurements.

| # | Commit subject | Files | What it does |
|---|---|---|---|
| 1 | `common, llama-bench : allow pinned host buffer types in --override-tensor` | `common/arg.cpp`, `src/llama-model-loader.cpp`, `tools/llama-bench` | `-ot` accepts `Vulkan_Host` and the other host buffer types; warns when mmap makes the override a no-op |
| 2 | `vulkan : add an fp32 variant of the lightning indexer ...` | `lightning_indexer.comp`, `vulkan-shaders-gen.cpp`, `ggml-vulkan.cpp` | reads K and the mask in 16 bits, computes in 32; the op no longer falls back to the CPU without `shaderFloat16` |
| 3 | `quantize : apply --tensor-type overrides in COPY mode` | `src/llama-quant.cpp` | `COPY` requantizes the named tensors and copies the rest |
| 4 | `vulkan : enable multi_add fusion on AMD drivers without RTE fp16` | `ggml-vulkan.cpp` | the fusion was tied to a float16 rounding feature although the shader is f32 only |
| 5 | `ggml-cpu : faster Q2_0 x Q8_0 mul_mat_id on AVX2 ...` | `ggml-cpu/arch/x86/quants.c`, `ggml-cpu.c`, `quants.h` | activations rearranged once per column to match the Q2_0 bit layout, weights prefetched ahead |
| 6 | `vulkan : sparse flash attention from 4x on GCN with Q8_0 K/V` | `ggml-vulkan.cpp`, `tests/test-backend-ops.cpp` | the sparse path starts when the cache is 4x the selection instead of 16x, on GCN only |
| 7 | `vulkan : GGML_VK_FIRST_SUBMIT_NODES ...` | `ggml-vulkan.cpp`, `ggml-vulkan-types.h` | separate node count for the first submit of a graph |
| 8 | `qwen4exp : optional reduced output vocabulary (d2t) for MTP draft files` | `src/models/qwen4exp.cpp` | loads `output.weight` with K rows when `d2t` is present and scatters the logits |
| 9 | `vulkan : q3_K / q5_K mat-vec, fold the scales into the weights once per row` | `mul_mat_vec_q3_k.comp`, `mul_mat_vec_q5_k.comp` | each B column becomes a plain dot product; 4 columns fit in 128 VGPRs |
| 10 | `vulkan : iq4_xs mat-vec, do the sub-block in two halves with 2+ columns` | `mul_mat_vec_iq4_xs.comp` | 16 values of B live per column instead of 32; 3 columns fit in 128 VGPRs |

### The register threshold behind patches 9 and 10

On GCN the vector registers of a SIMD are shared between the waves running on it: a shader that needs up to 128
VGPRs runs two waves at a time, one that needs more runs a single wave. The mat-vec shaders are compiled once per
number of B columns, and each column adds registers, so a variant can cross the line and cost far more than its
extra work explains. The other steps are at 64 and 84 VGPRs.

To see it for any shader:

```bash
RADV_DEBUG=shaderstats,nocache build/bin/test-backend-ops perf -b Vulkan0 -o MUL_MAT \
    -p 'type_a=iq4_xs,type_b=f32,m=10240,n=3,k=2560' 2>&1 | grep -E 'VGPRs|us/run'
```

(`m`, `n`, `k` only match shapes that exist in the perf list of `tests/test-backend-ops.cpp`; add yours there.)

| us/run, 10240x2560 | 1 col | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| q3_K before | 134 | 176 | 226 | 369 | 432 |
| q3_K now | 122 | 168 | 210 | 265 | 399 |
| q5_K before | 122 | 161 | 194 | 290 | 336 |
| q5_K now | 126 | 152 | 192 | 221 | 320 |
| iq4_xs before | 97 | 138 | 283 | 353 | 438 |
| iq4_xs now | 96 | 132 | 173 | 262 | 307 |

With 2 MTP drafts the verify batch has 3 columns, so the iq4_xs case was hit on every step. Fewer rows per
workgroup is not a way out: it gets under the threshold and is much slower (iq4_xs, 3 columns: 424 us with 4 rows,
779 with 2).

## Expected results

Temperature 0 unless noted, desktop off, memory clock pinned.

| | |
|---|---|
| Generation, short prompt | ~20 tok/s (sampled, single runs: 20.0, 20.9) |
| Generation at 12K of context | 19.8 tok/s |
| Generation at 30K of context | 18.4 tok/s |
| Generation at 61K of context | 18.0-18.2 tok/s (temp 0.8) |
| Long-prompt processing | 134 tok/s for 3K tokens, 92 tok/s for 61K |
| VRAM | 7.2 GiB idle with 64K; peak 7.49 GiB with a 61K prompt |
| Pinned memory (GTT) | 29.5 GiB |

Stock configuration for comparison (the settings that load the model without any tuning): 12.8 tok/s, 62 tok/s on a long prompt, 8K of
context.

## How to measure without fooling yourself

1. **Correctness first.** `build/bin/test-backend-ops test -b Vulkan0 -o MUL_MAT` (and `MUL_MAT_ID`) compares the
   GPU against the CPU. Here: 2592/2592 and 1160/1160.
2. **An op that is faster in isolation is not a faster model.** Twice a matmul improved 25-60 % in
   `test-backend-ops perf` and the model did not move. Always finish with an end-to-end comparison.
3. **End-to-end A/B:** temperature 0, the same saved context for every run (`/slots/0?action=save` / `restore`),
   and the versions alternated (old, new, old, new), several runs each. With sampling, MTP adds about ±5 % of noise
   between seeds: compare with at least three seeds per arm and look at the acceptance (`draft_n_accepted /
   draft_n` in the `timings` of the response) besides the speed.
4. **To compare two builds of the Vulkan backend without rebuilding the server,** point `LD_LIBRARY_PATH` at a
   directory holding the other `libggml-vulkan.so.1`.
5. **Measure with a long prompt.** VRAM pressure does not show with short ones. When llama.cpp asks for more VRAM
   than is free, the kernel puts the rest in GTT and "VRAM used" still looks fine: read `drm-memory-vram` and
   `drm-memory-gtt` in `/proc/PID/fdinfo/*`, or watch `mem_info_vram_used` and `mem_info_gtt_used` under
   `/sys/class/drm/card*/device/` during the whole run and keep the peak.
6. **The Vulkan perf logger (`GGML_VK_PERF_LOGGER=1`) serializes every op.** Use it for proportions between ops
   and for per-shape timings, not for absolute time per token.

## Things that were measured and did not help

So you do not have to try them again on similar hardware.

- **3 MTP drafts instead of 2.** Even after patches 9 and 10: at temp 0.8, 18.6 vs 19.6 tok/s at 12K, 17.1 vs
  18.2 at 20K, 16.6 vs 17.3 at 30K. It wins on some seeds and collapses on others.
- **80K of context.** VRAM reaches 7.99 GiB and prompt processing falls from ~26K on (56 tok/s at 43K and
  dropping). Going from 64K to 80K takes 0.5 GiB, twice what the K/V cache alone accounts for.
- **MTP draft in Q8_0** to use spare VRAM: same acceptance, 18.4 -> 14.6-15.4 tok/s (the draft's experts are read
  by the CPU, and Q8_0 doubles the bytes).
- **Expert cache in VRAM** (`--moe-cache-mib`): with ~0.9 GiB free for 31.6 GiB of experts it is always slower.
- **Skipping the lowest-weight experts** when verifying drafts, **pre-recording the Vulkan commands** of the next
  split, and **merging the draft catch-up decode into the next draft**: all within noise or worse.
- **Overclocking the memory.** The Polaris SMU hangs with a modified table.
- **`OMP_WAIT_POLICY=PASSIVE`, `GOMP_SPINCOUNT`, `--prio 2`:** all slower than the default busy wait.
